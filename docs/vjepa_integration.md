# Інтеграція V-JEPA 2 в OSTrack

Чернетка дизайну для обговорення в команді (власник дизайну fusion — Андрій, див. proposal §7).

## Чому саме так: що показали дані

- Після оклюзії довжиною 31–150 кадрів ціль з'являється в середньому за **2.5 розміру боксу** від місця,
  де зникла (`results/eda/reappearance.csv`, EDA розділ 7).
- Ділянка пошуку OSTrack — квадрат зі стороною 4 розміри цілі, тобто сягає лише **~2 розміри боксу** від
  центру. Після довгої оклюзії ціль часто поза нею.
- Baseline (результати авторів OSTrack-256, `results/ostrack_official/`): ORR 81.5% для оклюзій 1–5 кадрів,
  72.8% для 6–30, **50.6%** для 31–150, 45.5% для довших.

Отже, злиття ознак лише всередині ділянки пошуку допоможе з короткими оклюзіями й відволікачами. Для
довгих потрібно ще й переносити ділянку пошуку туди, де ціль з'явилася.

## Схема

```
кадри t-30, t-28, ..., t (лише минулі)
          │
     V-JEPA 2 ViT-L (заморожений), повний кадр 256×256
          │  раз на 8 кадрів, кешується (scripts/cache_vjepa.py)
          ▼
  мапа сцени F_t: 16×16×1024 на весь кадр
          │
          ├──► (A) RoIAlign під ділянку пошуку ──► 16×16×1024
          │                                          │
шаблон + ділянка ──► OSTrack backbone ──► 16×16×768 ──► [fusion] ──► голова OSTrack ──► бокс
пошуку               (заморожений)                     (навчається)   (заморожена)
          │
          └──► (B) пам'ять про ціль m = F усереднене в боксі цілі, поки трекер упевнений
                   cos(m, F_t) по всьому кадру ──► де ціль ──► перенести ділянку пошуку,
                   коли впевненість OSTrack низька
```

- **Повний кадр, а не фрагмент:** ознаки не залежать від трекера, тож рахуються один раз (план Б
  proposal: кешування). Роздільність: на test медіана **10.5 токенів V-JEPA на сторону ділянки
  пошуку**, менше 3 — лише в 11% кадрів (дрібні цілі).
- **Лише минулі кадри:** трекер онлайн, майбутнього не бачить (`clip_indices` у `src/vjepa/encoder.py`).

## Конфігурації

| | Що | Відповідає proposal |
|---|---|---|
| `fusion_v1` | компонент A: `x' = x + g·MLP([x; P(v)])`, `g = 0` на старті, тож до навчання = baseline | feature-level fusion |
| `fusion_v2` | A + пам'ять про ціль + компонент B (глобальний пошук) | друга конфігурація; B = план Б (post-hoc модуль) |

## Навчання

- Підмножина train зі збереженням балансу класів (напр. 4 відео/клас), кеш V-JEPA для них.
- Половина кадрів пошуку — одразу після повернення цілі, з ділянкою пошуку на останній позиції перед
  зникненням (там, куди дивився б реальний трекер).
- Втрати OSTrack (focal + GIoU + L1); для B — втрата на мапі схожості.
- OSTrack, V-JEPA і голова заморожені; навчається лише fusion (2–5 млн параметрів).

## Контрольні експерименти

1. **V-JEPA без руху:** у кліп подається той самий кадр 16 разів. Якщо приріст той самий, допомагає
   вигляд, а не відео-модель. Головна перевірка гіпотези.
2. `fusion_v1` проти `fusion_v2`.
3. ORR за довжиною оклюзії (`scripts/evaluate.py`).

## Перевірка до навчання

`scripts/vjepa_reid_check.py` (Kaggle: `notebooks/kaggle_vjepa.ipynb`): чи впізнає V-JEPA ціль після
оклюзії — найсхожіший токен на першому кадрі після повернення проти бокса цілі за розміткою і проти
місця, куди пішов OSTrack; з рухом і без. Якщо не впізнає, компонент B не спрацює.

## Ризики

- Дрібні цілі (11% кадрів): ознаки V-JEPA занадто грубі; варіант — модель з входом 384.
- Кеш: ~0.5 МБ на мапу; dev (40 відео) ≈ 7 ГБ; повний test потребує стиснення (PCA до 256 каналів).
- Предиктор V-JEPA 2 не використовуємо: він навчений відновлювати приховані ділянки, не прокручувати
  рух цілі вперед. Напрям на майбутнє.
